### 3-2. Claude → Codex 핸드오프 기록 형식

기존 `current.md`의 계획 섹션(목표/현재상태/구현계획/수용기준/예상변경파일/파일소유권/위험요소)은 그대로 유지하되, Codex가 사람에게 묻지 않고 판단할 수 있도록 문서 최상단에 **고정 필드 3개**를 추가한다.

```
**State:** planned
**기준 커밋:** <git rev-parse HEAD 값, Planner가 계획 작성 시점에 기록>
**승인 필요:** 아니오  |  예 (사유: <RULES.md 예외 카테고리 중 해당 항목>) — 사용자 승인: 대기 / 완료 (일시)
**최종 갱신:** Claude, <타임스탬프>
```

- **기준 커밋**: Planner가 계획을 작성한 시점의 `HEAD` 해시. Codex는 착수 전 현재 `HEAD`와 이 값을 비교해, 달라졌다면(다른 커밋이 그 사이 들어왔다면) 계획이 오래된 상태(stale)일 수 있다고 보고 착수하지 않는다 (3-5 참고).
- **승인 필요**: Planner가 `docs/RULES.md`의 예외 목록(대규모 리팩터링, 구조 변경, 새 의존성, 데이터 형식 변경, 프레임워크·모델 교체, 방향 변경, 민감정보/외부 시스템 영향)에 해당하는지 판단해 명시. "예"인 경우 사용자 승인이 "완료"로 기록되기 전까지 Codex는 `implementing`으로 전환할 수 없다 (3-6 참고).
- **최종 갱신**: 문서를 수정하는 쪽이 자기 이름과 시각으로 매번 갱신한다. 다른 에이전트는 자신이 마지막으로 읽었던 값과 비교해, 값이 달라져 있으면 "내가 안 본 변경이 있다"는 뜻으로 받아들이고 문서를 처음부터 다시 읽는다.

기존 "구현 결과"·"테스트 결과" 섹션의 형식을 아래처럼 표준화한다.

```
## 구현 결과
- 실제 변경 파일: <경로 목록>
- 계획 대비 변경 요약: <파일별 1~2줄>
- 계획 이탈 사항: 없음 | <있다면 무엇이 왜 달라졌는지>
- 종료 시점 git 상태: <`git status --porcelain` 요약 — Claude가 리뷰 시 대조용>

## 테스트 결과
- 실행 명령/검증: <명령어와 결과 요약>
- 수용 기준 체크리스트: <계획의 수용 기준 항목을 그대로 복사해 각각 pass/fail/미실행 표기>
- 미실행 항목과 사유: <있다면 기록>

**State:** implemented
**최종 갱신:** Codex, <타임스탬프>
```

- "계획 이탈 사항"을 반드시 명시하게 해서, Codex가 계획에 없던 파일을 건드렸거나 범위를 벗어났을 때 Claude가 diff만 보지 않고도 즉시 알아챌 수 있게 한다.
- "종료 시점 git 상태" 스냅샷을 남겨, Claude가 리뷰 시점의 실제 `git status`와 비교해 그 사이 다른 변경이 섞이지 않았는지 확인할 수 있게 한다.

### 3-4. State별 행동 규칙 (언제 일하고 언제 멈추는지)

| State | Claude가 할 일 | Codex가 할 일 |
|---|---|---|
| (State 없음/새 요청) | 5가지 확인 후 계획 작성, `planned`로 설정 | 대기 |
| `planned` + 승인 필요 아니오 (또는 승인 완료) | 대기 | 5가지 확인 후 착수, `implementing`으로 전환 |
| `planned` + 승인 필요 예, 승인 미완료 | 사용자에게 승인 요청, 대기 | **착수 금지**, 대기 |
| `implementing` | 대기 (Codex 소유 파일 건드리지 않음) | 계획된 파일만 구현 진행 |
| `implemented` | 5가지 확인 + diff·테스트 결과 검토 시작(`reviewing`) | 대기 |
| `reviewing` | 검토 진행 → 통과 시 `approved`, 문제 시 `implementing`으로 반려 + 수정 항목 기록 | 대기 (반려되면 그 항목만 재작업) |
| `approved` | 대기, 사용자 확인 요청 | 대기 |
| `verified` | 작업 종료. 새 요청이 오면 3-7 절차로 초기화 후 새 계획 작성 | 대기 |

원칙: **자기 차례가 아닌 State를 보면 어떤 파일도 수정하지 않고 대기하거나 상태만 보고한다.**

### 3-5. Stale State·불일치 감지 및 정지 규칙

다음 중 하나라도 해당하면, 발견한 에이전트는 **작업을 진행하지 않고 즉시 멈춘 뒤** 무엇이 불일치하는지 보고한다 (사용자 또는 상대 에이전트에게).

1. `기준 커밋`이 현재 `git rev-parse HEAD`와 다르다.
2. `최종 갱신` 담당자/시각이 자신이 마지막으로 확인했던 값과 다르다(= 자신이 못 본 변경이 있었다).
3. `git status`/`git diff` 결과가 `current.md`의 "예상 변경 파일" 또는 "구현 결과"에 없는 파일 변경을 포함한다.
4. `State` 값이 정의된 6개 값 중 하나가 아니거나, 필드가 비어 있거나 형식이 깨져 있다.
5. 같은 파일에 대해 소유권이 명시되지 않았거나, 이미 다른 에이전트가 진행 중인 State에서 자신이 그 파일을 건드리려 한다.

### 3-6. 승인 필요 작업에서 Codex 자동 착수 방지

- Planner는 계획 작성 시 `docs/RULES.md`의 예외 목록에 해당하는지 반드시 판단하고, 해당하면 `승인 필요: 예 (사유: ...)`로 명시하며 `사용자 승인: 대기`로 둔다. State는 계획이 끝난 상태이므로 여전히 `planned`이지만, 이 필드가 "대기"인 동안 Codex는 진행하지 않는다.
- 사용자가 승인 의사를 밝히면(대화로 Claude에게 말하거나, 직접 문서를 확인 후 알려주는 방식 모두 가능), **`사용자 승인: 완료 (일시)`로 필드를 바꾸는 주체는 사용자의 승인 발언을 받은 쪽(주로 Claude)이다.** Codex는 스스로 이 필드를 "완료"로 바꿀 수 없다 — 자기 자신의 착수 조건을 스스로 승인 처리하지 못하게 막는 것이 핵심이다.
- Codex의 착수 전 점검 항목(다음 구현 단계에서 `AGENTS.md`에 명시): "`State: planned`이고 `승인 필요: 아니오` 이거나 `승인 필요: 예`이면서 `사용자 승인: 완료`일 때만 `implementing`으로 전환한다."

### 3-7. `verified` 이후 초기화 절차

- `docs/tasks/current.md`는 git으로 버전 관리되므로, 원칙적으로 매 `verified` 시점의 내용은 git 히스토리에 남는다 — **단, 그 시점에 실제로 커밋이 이뤄졌을 때만 그렇다.** 이 저장소는 커밋이 자동화돼 있지 않으므로(사용자가 `/깃업데이트`를 수동 실행), 커밋 전에 문서를 덮어쓰면 이전 내용이 완전히 사라질 위험이 있다.
- 이를 보완하기 위해, 새 작업을 시작하며 `current.md`를 초기화하기 직전에 Planner(Claude)는 직전 `verified` 내용을 `docs/tasks/archive/<완료일자>-<간단슬러그>.md`로 복사해 보관한 뒤 `current.md`를 빈 템플릿(목표/변경대상 "없음" 등, 최초 상태와 동일한 형태)으로 재설정한다.
- `docs/tasks/archive/` 디렉터리 신설은 신규 구조 추가로 볼 수 있어, **다음 구현 단계에서 실제로 만들기 전 사용자 승인을 받는 항목으로 분류한다** (이번 설계 문서에는 절차만 기록).
- 초기화 후 새 계획을 작성할 때까지 `State` 필드와 3개 고정 필드(기준 커밋/승인 필요/최종 갱신)는 비워두거나 "없음"으로 표시해, 이전 작업의 값이 새 작업에 실수로 남아 있는 상태를 방지한다.

## 4. 수용 기준

- 5가지 사전 확인 체크리스트(문서 4개 + git 확인)가 `AGENTS.md`에 명시되어, Claude와 Codex가 각자 무엇을 확인해야 하는지 표로 구분된다.
- `docs/tasks/current.md`의 표준 템플릿에 `기준 커밋`/`승인 필요`/`최종 갱신` 3개 고정 필드가 추가된다.
- Codex→Claude 핸드오프 형식(계획 이탈 사항, 종료 시점 git 상태 포함)이 문서화된다.
- State별로 "누가 무엇을 하고 언제 멈추는지"가 표로 명시된다.
- Stale/불일치 감지 조건 5가지와 "발견 시 즉시 멈추고 보고한다"는 원칙이 문서화된다.
- 승인 필요 작업에서 Codex가 `사용자 승인: 완료` 없이는 `implementing`으로 전환하지 않는다는 규칙, 그리고 이 필드를 Codex 스스로 완료 처리할 수 없다는 제약이 문서화된다.
- `verified` 이후 초기화 절차(아카이브 포함)와 그 절차 중 신규 디렉터리 생성은 별도 사용자 승인이 필요하다는 점이 문서화된다.
- 이번 단계에서 오케스트레이터, 자동 호출 스크립트, 상태 자동 검사 도구는 만들어지지 않는다 — 전부 사람이 읽고 따르는 문서 규칙이다.
- 제품 코드는 변경되지 않는다.
- `CODEX.md` 등 신규 역할 파일은 만들지 않는다(3-1-1 결정에 따름).

## 7. 위험 요소 또는 주의사항

- 고정 필드가 늘어날수록 Planner/Builder가 매번 채워야 할 항목이 많아진다 — 이번 설계에서는 꼭 필요한 3개(기준 커밋/승인 필요/최종 갱신)로 최소화했다.
- "최종 갱신자/시각" 필드는 진짜 파일 잠금이 아니라 관례일 뿐이다 — 두 에이전트가 동시에 문서를 열람·수정하는 경합 상황을 완전히 막지는 못한다. 완전한 동시성 제어는 오케스트레이터 없이는 불가능하므로 이번 설계의 한계로 남긴다.
- `기준 커밋` 비교가 의미 있으려면 Codex/Claude가 실제로 `git rev-parse HEAD`를 확인하는 습관이 지켜져야 한다 — 이를 강제할 자동화 장치는 없고, 역할 문서의 체크리스트로만 안내한다.
- Codex는 외부 도구이므로 이 저장소의 문서 규칙을 "읽었는지" 시스템적으로 강제할 수 없다 — 규칙 준수 여부는 결국 Codex를 실행하는 사용자(또는 Codex 쪽 설정)에 달려 있다는 한계를 인지해야 한다.
- `docs/tasks/archive/` 신설은 작더라도 구조 변경이라, 다음 구현 단계에서 실제로 만들기 전에 반드시 사용자 확인을 다시 받는다(이번 계획에 이미 반영함).
- 초기화 절차(3-7)가 있어도, 사용자가 `/깃업데이트`로 커밋해두지 않으면 archive 파일 자체도 로컬에만 남는다 — 완전한 백업이 되려면 결국 git 커밋/푸시가 필요하다는 점을 사용자에게 안내해야 한다.
