## 1. 목표

이번 작업의 목표는 **하나**다 — 직전 사이클에서 FAIL한 수용 기준 ③(실제 종료 전 100% 도달 금지) 하나만 고친다. `duration - 0.1` 같은 임의의 시간 여유값으로 우회하지 않고, **실제 EOF가 Python 쪽에서 확인되기 전에는 클라이언트 보간만으로 100%를 확정하지 않으며, 실제 EOF가 확인된 순간에만 정확히 100%가 되는 구조**로 고친다.

**반드시 보존해야 하는, 이미 정상 동작하는 사항(회귀 금지)**:
- 부드러운 재생바 애니메이션, 클릭/드래그 seek, 재생/일시정지
- 실제 프레임 위치로의 재동기화(`checkSync()` 메커니즘)
- 주기적 `st.rerun()`/`st.fragment(run_every=...)` 없음

**명시적 제외 범위(이번 작업으로 확대하지 않음)**: YOLO 추론 속도, OpenVINO, `FRAME_SKIP`, `AsyncDetectorWorker` 등 영상 재생 속도·탐지 성능 개선은 이번 작업에서 전혀 다루지 않는다(아래 "### 후속 작업 메모" 참고). 재생바 UX(디자인·부드러운 이동·seek) 자체의 재설계도 하지 않는다 — 오직 EOF 경계 조건만 고친다.

## 2. 현재 상태 (직전 사이클 구현 + 이번에 조사한 FAIL 원인)

- 직전 Codex 사이클이 이미 다음을 구현해 제품 코드에 반영했다(그대로 유지):
  - `pages/1_모니터링.py`: `while` 루프 안, 정상적으로 새 프레임을 읽은 매 반복(900~909행)마다 `sync_ph.markdown(...)`으로 `data-pos/data-dur/data-playing/data-now/data-seq`를 rerun 없이 발행한다.
  - `core/playback_bar_component.py`: `requestAnimationFrame` 루프에 `checkSync()`를 추가해 새 `data-seq`를 받을 때마다 `base`/`anchor`/`duration`/`playing`을 재동기화하고, `position()`이 `Math.min(base + elapsed, duration)`으로 계산한다(모듈로 제거 완료).
- **Codex 자체 테스트로 재현된 FAIL(③)**: 실제 위치 14.95초(전체 15초)에서 다음 동기화 없이 60ms만 경과해도 `position()`이 `duration`(15초=100%)에 도달한다.
- **직접 코드 조사로 확인한 근본 원인 — "실제 EOF 확인" 신호 자체가 존재하지 않는다**:
  1. **Python 쪽 EOF 감지 지점(`pages/1_모니터링.py` 776~778행)**: `ret, frame = vs.read_frame()`; `if not ret: vs.reset(); continue` — 이 분기가 실제 EOF를 감지하는 유일한 지점인데, 곧장 `continue`로 루프 처음으로 돌아가 버려서 "지금 실제로 끝났다"는 사실을 `sync_ph`로 전혀 발행하지 않는다. `sync_ph` 발행은 오직 정상적으로 새 프레임을 읽은 경우(900~909행)에만 일어난다.
  2. **JS 쪽 보간(`core/playback_bar_component.py`의 `position()`)**: `Math.min(base + elapsed, duration)`은 "실제 EOF가 확인됐는지"를 전혀 모른 채, 마지막 실제 동기화 이후 시간이 충분히 지나면(실측 배속이 1x보다 느리므로 흔히 발생) `duration`에 도달해버린다.
  - 즉 Python은 EOF를 감지하고도 알리지 않고, JS는 그 사실을 모른 채 경과 시간만으로 100%를 추정한다 — `duration - 0.1` 같은 여유값은 배속이 달라지면 여전히 틀릴 수 있는 임시방편이라 채택하지 않는다. 필요한 건 "실제 확인된 값 이상으로는 추정하지 않는다"는 구조적 규칙이다.

## 3. 구현 계획 (이번 좁힌 범위 — ③번 FAIL만 수정)

1. **Python (`pages/1_모니터링.py`, 776~778행 `if not ret:` 분기)**: `vs.reset()` 하기 직전에, 실제로 끝났다는 것을 알리는 EOF 확인 신호를 한 번 발행한다:
   ```python
   if not ret:
       if not is_rtsp and total_video_frames > 0:
           sync_ph.markdown(
               f'<div id="safeview-playback-sync" '
               f'data-pos="{total_video_frames/fps:.3f}" data-dur="{total_video_frames/fps:.3f}" '
               f'data-playing="{str(not st.session_state.paused).lower()}" '
               f'data-now="{time.time()*1000:.0f}" data-seq="{frame_idx}-eof" '
               f'data-eof="true" '
               f'style="display:none"></div>', unsafe_allow_html=True)
       vs.reset(); continue
   ```
   `data-seq`에 `-eof` 접미사를 붙여 직전 정상 프레임 발행의 seq와 반드시 달라지게 한다(같으면 JS가 "변경 없음"으로 판단해 무시함). 이것도 기존과 동일한 `st.empty().markdown()` rerun-free 갱신이며 `st.rerun()`이 아니다.
2. **Python (900~909행, 기존 정상 발행)**: 같은 div에 `data-eof="false"`를 추가한다 — 실제 새 프레임이 처리될 때마다 "아직 끝나지 않았다"를 명시적으로 갱신하며, EOF 이후 반복재생으로 다음 정상 프레임이 오면 이 값이 자연스럽게 다시 `false`로 돌아간다.
3. **JS (`core/playback_bar_component.py`)**: `checkSync()`가 `data-eof`를 읽어 `eofConfirmed` 상태(`true`/`false`)를 갱신한다. `position()`을 다음과 같이 바꾼다:
   ```js
   function position() {
     const elapsed = playing ? (performance.now() - anchor) / 1000 : 0;
     const projected = base + elapsed;
     // 실제 EOF 미확인 상태에서 duration에 도달하려 하면, 추정하지 않고
     // 마지막으로 확인된 실제 위치(base)에서 멈춘다.
     if (!eofConfirmed && projected >= duration) return base;
     return Math.min(projected, duration);
   }
   ```
   보간이 `duration`에 다다르려는 순간에도 실제 EOF가 미확인이면 마지막 실측 위치(`base`)에서 대기하고, 실제 EOF가 확인되는 즉시(`eofConfirmed===true`) 정확히 `duration`(100%)을 반환한다. 이는 "duration에서 임의의 시간을 뺀 여유값"이 아니라 "실제로 확인된 값 이상 추정하지 않는다"는 구조적 규칙이라 재생 배속이 얼마든 항상 성립한다.
4. **되감기(EOF→반복재생) 경로**: `vs.reset()` 이후 다음 반복에서 정상적으로 읽히는 첫 프레임이 `data-pos`≈0, `data-eof="false"`로 다시 발행된다 — `checkSync()`가 이를 받으면 `eofConfirmed`를 다시 false로, `base`를 0 근처로 되돌린다. 로컬에서 모듈로 연산 등으로 추측해 되감지 않는다(직전 사이클과 동일 원칙 유지).
5. 이 두 파일 외에는 건드리지 않는다. 시크 처리, 재생/일시정지, `reset_parked()`, 탐지·판정·이벤트·페이싱 로직, 클릭/드래그 seek 프로토콜, 애니메이션 루프 구조는 직전 사이클에서 이미 구현된 그대로 보존한다 — 이번 수정은 EOF 신호 발행 한 곳(+정상 발행에 `data-eof="false"` 한 속성 추가)과 `position()`/`checkSync()`의 EOF 처리 부분만 추가/변경한다.

## 4. 수용 기준 (이번 좁힌 범위 — ③번 재검증 + 기존 PASS 항목 회귀 없음)

- [ ] **EOF 직전에는 100%가 아니다**: 실제 마지막 프레임 이전 위치에서 다음 실제 프레임 없이 시간이 충분히 지나도, 재생바가 100%로 표시되지 않고 마지막으로 확인된 실제 위치에서 멈춰 있는다(위 14.95초+60ms 경계 조건 재현 안 됨).
- [ ] **실제 EOF에서는 정확히 100%다**: `vs.read_frame()`이 EOF를 반환하는 순간(계획 3-1) 발행되는 신호를 받으면, 재생바가 즉시 정확히 100%(=duration)로 표시된다.
- [ ] **끝에서 0으로 되돌아가지 않는다(로컬 추측 되감기 재도입 없음)**: EOF 이후 `vs.reset()`으로 영상이 실제로 처음부터 다시 재생될 때만, 그 실제 새 프레임의 `data-pos`를 받아 재생바가 0 근처로 이동한다.
- [ ] **seek/재생/일시정지 기존 동작이 그대로 유지된다**: 클릭/드래그 seek, 재생↔일시정지 전환, 부드러운 애니메이션에 회귀가 없다(직전 사이클에서 이미 PASS한 항목 — 이번 수정으로 깨지면 안 됨).
- [ ] **새로운 주기적 `st.rerun()`/`st.fragment(run_every=...)`가 추가되지 않는다**: 이번에 추가하는 EOF 신호도 기존과 동일하게 `st.empty().markdown()` 기반 rerun-free 갱신이다.
- [ ] `duration`에서 임의의 시간(예: `duration - 0.1`)을 빼는 방식으로 우회하지 않았다 — `eofConfirmed`(실제 EOF 확인 여부) 기준으로 판단하는 구조인지 코드 리뷰에서 확인한다.
- [ ] 직전 사이클에서 이미 PASS 확인된 항목(먼저 끝에 도달 안 함, EOF 반복 반영, 주기적 rerun 없음, 변경 파일 범위 준수)에 회귀가 없다.
- [ ] YOLO 추론·위험 판정·ROI·이벤트 저장·OpenVINO 백엔드·RTSP 동작에 회귀가 없다 — 이번 작업 범위를 YOLO 성능이나 영상 재생 속도 개선으로 확대하지 않는다.
- [ ] `pages/1_모니터링.py`, `core/playback_bar_component.py` 외의 파일은 변경되지 않는다(`docs/tasks/current.md` 제외).

**최종 확인(필수)**: 사용자가 실제 영상으로 재생 끝부분(EOF 부근)을 포함해 충분히 긴 시간 재생하며 위 경계 조건을 직접 확인해야 `verified` 전환이 가능하다.

## 7. 위험 요소 또는 주의사항

- **이번 작업 범위는 수용 기준 ③(실제 종료 전 100% 도달 금지) 수정 하나로 한정한다** — 재생바 UX 재설계, YOLO 속도·OpenVINO·`FRAME_SKIP`·`AsyncDetectorWorker` 관련 사항은 절대 건드리지 않는다. 관련 조사 메모는 아래 "### 후속 작업 메모 — 영상/탐지 성능(별도 작업, 이번 범위 아님)"에 남겨 다음 작업이 그대로 이어받을 수 있게 했다.
- **`duration - 0.1` 같은 임의의 시간 여유값으로 우회하지 않는다** — 실제 EOF 확인 여부(`eofConfirmed`)를 기준으로 판단하는 구조인지 리뷰에서 반드시 확인한다. 여유값 방식은 배속이 달라지면 다시 틀릴 수 있어 채택하지 않는다.
- EOF 신호 추가가 기존에 이미 PASS한 항목(부드러운 이동, seek, 재동기화, 반복재생, rerun 금지)을 깨뜨리면 안 된다 — `checkSync()`/`position()` 변경이 최소한으로 국한됐는지, 정상 동기화 경로(EOF 아닌 경우)의 기존 동작이 그대로인지 리뷰에서 확인한다.
- 숨김 DOM 요소를 통한 재동기화는 `window.parent.document` 접근에 의존한다 — 이미 여러 차례(4차 반려 PoC, 클릭/드래그 이벤트 처리 등) 같은 방식으로 정상 동작을 확인했으므로 위험도는 낮다고 판단한다.
- "코드 레벨 PASS"만으로 사용자 검증을 대체하지 않는다 — 이번에도 실제 화면(충분히 긴 재생)에서 최종 확인 후 `verified` 전환한다.

### 후속 작업 메모 — 영상/탐지 성능 (별도 작업, 이번 범위 아님)

이번 재생바 작업이 `verified`로 종료된 뒤, 별도 작업으로 다룰 조사 항목(5차 반려 대응 A/B 조사에서 이미 확인·발견한 것):

사용자가 실제 브라우저에서 확인한 결과, 아래 3가지는 정상 동작한다:
1. 막대가 슬라이더 하나만 보이고 시:분:초로 정확히 표시됨(`datetime.time` + `format="mm:ss"`가 Streamlit 1.55.0에서 잘 렌더링됨 — 리뷰가 남긴 "렌더링 미검증" 우려는 해소됨).

3. 재생 중 실시간 텍스트("MM:SS / MM:SS")도 정상 갱신됨.

**반려 사유**: 다만 **재생 중에 슬라이더(막대) 자체는 전혀 움직이지 않는다.** 사용자가 원하는 동작은 "재생 중 재생바가 진행 위치로 계속 이동하는 것"이다 — 지금은 슬라이더가 멈춰 있고 그 옆/아래 텍스트만 실시간으로 바뀌는데, 이건 유튜브 재생바가 실제로 채워지며 이동하는 것과는 다르다. 사용자 표현: "슬라이더 드래그로 실제 탐색이 정확히 돼. 하지만 재생 중 재생바가 움직이진 않아. 내가 원하는 건 재생 중 재생바가 진행위치로 이동하는거야."

**근본 원인**: `st.slider`는 Streamlit 위젯이라 화면에 그려진 뒤에는 **전체 스크립트가 다시 실행돼야만** 새 값으로 다시 그려진다. 지금 구조(`while st.session_state.running:` 네이티브 파이썬 루프)는 매끄러운 영상 재생을 위해 재생 중에는 전체 스크립트를 다시 실행하지 않도록 설계돼 있어서, 슬라이더가 재생 중 고정된 채로 남는다. 이번 계획(2차)에서 텍스트로 실시간 피드백만 보완했는데, 사용자가 원한 건 텍스트가 아니라 **막대 자체의 움직임**이었다.

**요청하는 수정 방향**: 재생 중에도 슬라이더(막대)가 실제로 진행 위치로 움직이도록 만든다. 정확한 구현 방식은 Codex가 실제 환경(Streamlit 1.55.0)에서 검증 후 정하되, 최소한 아래 두 방향을 검토한다:
- **(a) 주기적 전체 재실행**: `while` 루프 안에서 일정 주기(예: 1초)마다 `st.rerun()`을 호출해 슬라이더를 포함한 화면 전체를 다시 그린다. 매 프레임이 아니라 주기적으로만 호출하므로 영상 디코딩/표시 자체(별도 placeholder 기반)는 계속 매끄럽게 동작해야 한다 — 다만 재실행 시점에 아주 짧은 끊김(hitch)이 생길 수 있는지 실제로 확인이 필요하다.
- **(b) `st.fragment(run_every=...)` 사용**: 슬라이더 부분만 별도 프래그먼트로 감싸 주기적으로 독립적으로 재실행되게 한다(Streamlit 1.33+ 지원, 이 프로젝트는 1.55.0이라 사용 가능). 전체 페이지가 아니라 그 프래그먼트만 다시 그려지므로 이론적으로 더 가볍다. 다만 **메인 스크립트가 네이티브 `while` 루프에 계속 머물러 있는 상태에서 프래그먼트의 주기적 재실행이 실제로 끼어들어 동작하는지**(Streamlit의 실행 모델상 가능한지)는 실제로 검증이 필요하다 — 만약 안 되면 (a)로 폴백한다.

어느 방식이든 다음을 반드시 지킨다:

- 재실행 주기(예: 1초)는 시작값이며, 너무 잦으면 성능에 영향을 줄 수 있고 너무 뜸하면 "움직이는 느낌"이 안 날 수 있다 — Codex가 합리적인 값을 정하되 근거를 기록한다.

**근본 원인**: `st.rerun()`은 Streamlit 스크립트를 "부분 갱신"하는 게 아니라 **현재 실행을 즉시 중단하고 스크립트 전체를 처음부터 다시 실행**시키는 호출이다. 이 페이지의 슬라이더는 while 루프 진입 **이전**(694행 이후, 재생 컨트롤 UI 블록)에 생성되므로, 매 rerun마다 다음이 전부 다시 실행된다:
- `frame_ph`/`video_progress_ph` 등 주요 placeholder(`st.empty()`) 재생성(616~619행) — 화면 깜빡임의 직접 원인으로 보인다(기존 DOM 노드가 사라졌다 다시 채워지는 것으로 보임).
- `load_roi(...)` 디스크 I/O(677행), 처리 해상도 축소 비율 재계산(684~692행), 슬라이더 위젯 자체의 재생성(694행 이후) 등 원래 루프 진입 전 "한 번만" 실행되도록 의도된 준비 작업 전체.
- 이 모든 재실행 비용이 매초 프레임 처리·표시 사이에 끼어들어, 영상이 매끄럽게 재생되지 않고 끊기는 현상(사용자가 보고한 "느리게 재생되고 뚝뚝 끊김")으로 이어지는 것으로 보인다.

### 실제 사용자 실기 검증 결과 4차 반려 (2026-09-24, State: `approved` → `implementing`)

**증상(사용자 원문)**: 실제 영상 재생 시 다음 오류 발생.
```
RuntimeError: module is None. This should never happen.
```
발생 위치: `pages/1_모니터링.py` 825행 `declare_component("safeview_playback", path=_playback_assets().name)`. Streamlit 내부 `component_registry.py`의 `_get_module_name(caller_frame)`에서 `inspect.getmodule(caller_frame)`이 `None`을 반환해 발생.

**근본 원인 (설치된 Streamlit 1.55.0 소스와 Python 3.13.7 `inspect` 표준 라이브러리 소스로 직접 추적, 추정이 아닌 코드 근거)**:

1. `app.py`는 `st.Page("pages/1_모니터링.py", ...)`처럼 **파일 경로 문자열**로 페이지를 등록하고 `st.navigation([...]).run()`으로 실행한다(89~97행).
2. Streamlit의 `StreamlitPage.run()`(`streamlit/navigation/page.py` 374~381행)은 파일 경로 페이지를 실행할 때 다음과 같이 동작한다:
   ```python
   code = ctx.pages_manager.get_page_script_byte_code(str(self._page))
   module = types.ModuleType("__main__")
   module.__dict__["__file__"] = str(self._page)
   exec(code, module.__dict__)
   ```
   즉 **매번 새 `types.ModuleType` 객체를 만들어 그 안에서 페이지 코드를 `exec()`하지만, 이 module 객체를 `sys.modules`에 등록하지 않는다.**
3. `declare_component()`(`component_registry.py` 33~50행)는 호출자의 모듈을 알아내려고 `inspect.getmodule(caller_frame)`을 호출한다. Python 표준 라이브러리 `inspect.getmodule()`은 프레임 객체를 받으면 `__module__` 속성이 없으므로 파일 경로 기반으로 `sys.modules`를 순회 검색하는데, 위 2번 때문에 **`sys.modules`에 해당 페이지 파일과 일치하는 모듈이 존재하지 않아** 결국 `None`을 반환한다. 프레임 객체는 `__name__` 속성도 없어 마지막 폴백(`sys.modules['__main__']` 확인)도 통과하지 못하고 그대로 `None`이 된다.
4. `component_registry.py`는 `module is None`이면 무조건 `RuntimeError("module is None. This should never happen.")`을 던진다 — 정확히 사용자가 본 오류.

**질문별 확인 결과**:
- **PoC는 왜 성공했는데 실제 앱은 실패하는가**: 1단계 PoC의 `app.py`는 `streamlit run app.py`로 직접 실행되는 진짜 최상위 스크립트라 Python/Streamlit이 이를 정상적으로 `sys.modules['__main__']`에 등록한다. 반면 실제 제품은 `pages/1_모니터링.py`가 `st.navigation`+`st.Page(파일경로)`+`.run()`을 통해 위 3번 방식으로 실행되므로, PoC가 검증한 "declare_component가 되는 환경"과 실제 제품이 declare_component를 호출하는 환경이 근본적으로 다르다. **이건 1단계 PoC 설계의 결함이다** — 실제 멀티페이지 구조를 재현하지 않고 단일 스크립트로만 검증했기 때문에 이 문제를 미리 잡아내지 못했다.
- **Streamlit 1.55.0에서 멀티페이지 페이지 내부에서 declare_component를 호출하는 방식 자체가 문제인가**: 그렇다. `st.Page(파일경로)` + `.run()` 메커니즘의 `exec()` 방식이 근본 원인이며, 이 프로젝트나 이번 구현만의 문제가 아니라 Streamlit의 해당 페이지 실행 메커니즘 자체의 구조적 특성이다.
- **declare_component를 별도의 import 가능한 모듈에 선언하고 페이지에서는 이미 선언된 함수를 import해서 쓰는 구조가 정식/안전한 해결책인가**: 그렇다. Streamlit 공식 커스텀 컴포넌트 관례 자체가 "별도 모듈에서 `declare_component`를 한 번만 호출하고, 그 결과 함수를 wrapping해 export"하는 패턴이다(`declare_component`의 자체 docstring도 "import it from the module"을 언급). 이 프로젝트에 적용하면: `declare_component(...)` 호출을 `pages/1_모니터링.py` 밖의 일반 Python 모듈(예: `core/` 하위 새 모듈)로 옮기고, 그 모듈은 Python의 표준 `import` 문으로 로드되므로(= `sys.modules`에 정상 등록됨) 해당 모듈의 최상위 코드에서 실행되는 `declare_component` 호출의 caller frame은 `inspect.getmodule()`로 정상 해석된다. `pages/1_모니터링.py`는 이렇게 만들어진 컴포넌트 호출 함수만 `import`해서 사용하면 된다.
- **PoC에서 검증한 JS/컴포넌트 메커니즘은 그대로 두고 선언 위치만 바꾸는 최소 수정으로 가능한가**: 그렇다. 문제는 오직 "`declare_component()`가 어느 모듈의 최상위 코드에서 호출되는가"이지, 컴포넌트의 HTML/CSS/JS 내용이나 `Streamlit.setComponentValue` 프로토콜, wall-clock 보간 방식과는 무관하다. 기존에 검증된 프런트엔드 자산(`_playback_assets()`가 만드는 `index.html` 등)과 이벤트 처리 로직은 그대로 재사용하고, **`declare_component(...)` 호출 위치만 별도 모듈로 옮기는 최소 변경**으로 해결 가능하다고 판단한다.

**재발 방지 — 다음 시도 전 최소 재현 검증 필수**: 이번 실패는 "PoC에서 성공 → 실제 제품에서 실패"가 4번째 반복된 패턴이다(1~3차는 while 루프 재실행 문제, 이번은 멀티페이지 모듈 등록 문제로 원인은 다르지만 패턴은 같다). 이번엔 제품 코드를 다시 건드리기 전에, **실제 프로젝트와 동일한 구조(`app.py` → `st.navigation([st.Page("pages/x.py")])` → `pg.run()` → 페이지 내부)를 저장소 밖에 그대로 재현한 최소 PoC**에서 다음을 먼저 검증한다:
1. `declare_component`를 페이지 파일 안에서 직접 호출하면 동일한 `RuntimeError`가 실제로 재현되는지(원인 확정의 최종 확인).

### 재생바 동기화 최소 검증 PoC 결과 (Claude, 2026-09-25, 제품 코드 미수정)

5차 반려 조사에서 특정한 동기화 버그("재생바가 벽시계 1배속을 가정하지만 실제 재생은 그보다 느려 먼저 끝에 도달")를 고치기 위해 제안한 방식 — **rerun 없이 매 프레임 숨김 DOM에 실제 위치를 발행 + 컴포넌트의 기존 `requestAnimationFrame` 루프에서 그 값을 읽어 재동기화 + `% duration` 대신 `Math.min(pos, duration)` 클램프** — 을 실제로 구현하기 전에, 이 방식이 (a) 실제 Streamlit 구조에서 동작하는지, (b) 새로운 성능 저하를 만들지 않는지를 저장소 밖 격리 PoC로 검증했다. 제품 코드(`pages/1_모니터링.py`, `core/playback_bar_component.py`)는 이 과정에서 전혀 수정하지 않았다.

**방법**: 임시 디렉터리(`safeview-syncpoc-*`, 검증 후 완전히 삭제함)에 실제 프로젝트와 같은 방식(모듈 최상위에서 `declare_component` 1회 선언)으로 만든 최소 컴포넌트를 구성했다. `DURATION_S=15.0`짜리 가상 영상이 실제 배속의 절반(`TRUE_SPEED_RATIO=0.5`)으로만 진행되는 상황을 시뮬레이션해, 220회 반복 루프에서 매 반복마다 `frame_ph.image(...)`를 호출하고(실제 제품의 프레임 표시와 동일한 자리), `ENABLE_SYNC`가 켜져 있으면 그 직후 숨김 `sync_ph.markdown(...)`으로 `data-pos/data-dur/data-playing/data-now/data-seq`를 발행했다. 컴포넌트 JS는 기존 `requestAnimationFrame` 루프에 `checkSync()`를 추가해 `data-seq`가 바뀔 때마다 `base`/`anchor`를 재설정하고, 위치 계산은 모듈로 없이 `Math.min(p, duration)`로 클램프했다. 재동기화 이벤트·주기 상태를 별도 로그 서버(표준 라이브러리만 사용)로 전송해 기록했고, 헤드리스 브라우저 구동은 새 패키지 설치 없이 표준 라이브러리 기반 CDP 클라이언트로 직접 수행했다.

**결과 1 — 동작 정확성**: 재동기화 시 오차(`errBeforeResync`, 재동기화 직전까지 벌어졌던 표시값과 실제값의 차이)는 최초 1회만 약 0.5초(`maxErrorSeen: 0.4992`)였고, 이후 모든 재동기화에서 0.05~0.1초 수준으로 유지되며 더 커지지 않았다. 시뮬레이션 전체(15초 분량, 실제 배속 0.5x 기준 약 30초 wall-clock)에서 표시 위치가 실제 `duration`에 도달하기 전에 먼저 끝(모듈로로 인한 wraparound)에 닿는 일은 발생하지 않았다 — `Math.min` 클램프 적용 후 `wrapEvents`(클램프가 없었다면 wraparound가 발생했을 시점)는 누적됐지만 실제 표시값에는 영향이 없었다(클램프된 값에 머무름).
**결과 2 — 성능 영향**: 220회 반복 기준 평균 반복 시간이 sync 비활성화 153.04ms(최대 173.56ms) vs sync 활성화 153.43ms(최대 158.72ms)로, 평균 차이 약 0.4ms(약 0.25%)에 불과해 측정 잡음 수준이었다. 최대값은 오히려 sync 활성화 쪽이 더 낮게 나왔다(단일 실행 기준이라 이 역전 자체에 의미를 두지는 않지만, 적어도 sync 추가로 인한 유의미한 지연은 관찰되지 않았다).

**결론**: 제안한 동기화 방식은 실제 Streamlit 구조(모듈 최상위 `declare_component` + rerun-free `st.empty()` 갱신 + 컴포넌트 자체 `requestAnimationFrame` 폴링)에서 의도대로 동작하며, 추가 오버헤드는 무시할 수준이다. 제품 코드 적용을 진행해도 안전하다고 판단한다 — 다만 실제 파이프라인(진짜 YOLO 추론 부하, 진짜 영상 디코딩)과 결합했을 때도 이 결론이 유지되는지는 위 "## 4. 수용 기준"의 최종 확인(사용자 실제 영상 검증)에서 재확인한다. PoC에 사용한 모든 임시 파일·브라우저 프로세스·서버는 검증 직후 전부 정리했고, 정리 후 `git status --short`로 제품 저장소가 조사 전과 동일한 상태(이 문서만 변경)임을 재확인했다.
