## 3. 구현 계획

### 1번: FPS 중복

1. **우선 시도 — 구조적 격리**: `st.fragment(run_every=...)`(Streamlit 1.55에서 사용 가능)를 이용해 FPS 표시를 별도의 독립 프래그먼트로 분리하는 방법을 시도하라. 예: `st.session_state.fps_display`를 읽어서 "**FPS** &nbsp; {value}"만 그리는 짧은 함수를 `@st.fragment(run_every="1s")`로 감싸고, settings_col 안에서 한 번 호출한다. 이러면 메인 스크립트의 블로킹 while 루프나 재생/일시정지 버튼의 `st.rerun()`과 무관하게, 이 프래그먼트 혼자서 독립적인 주기로 자기 자신만 다시 그린다 — 지금처럼 `fps_ph = st.empty()`를 만들고 while 루프 안에서 수동으로 갱신하는 코드(602~606행, 864~866행)는 제거한다.
   - **중요**: 이 앱은 영상 재생 중 전체 스크립트가 `while st.session_state.running:` 블로킹 루프 안에 오래 머무르는 특이한 구조다. `st.fragment(run_every=...)`가 이런 블로킹 루프와 공존할 때 실제로 독립적으로 재실행되는지 — 즉 FPS 값이 살아있는 숫자로 바뀌는지 — **반드시 실제로 검증**하라. 만약 fragment가 메인 루프에 막혀 전혀 갱신되지 않는다면(가능성 있음), 이 방법은 포기하고 2번으로 간다.
2. **대안/진단 로그**: 1번이 제대로 동작하지 않거나, 동작은 하지만 여전히 두 줄 중복이 의심되면, 다음을 추가하라 — `fps_ph = st.empty()`(또는 이를 대체하는 요소)가 **생성될 때마다** 고유 ID(예: `uuid.uuid4().hex[:8]` 또는 `time.time()`)와 함께 `logs/` 밑의 임시 디버그 파일(예: `logs/fps_ph_debug.log`, 운영 코드에 영구히 남기지 말고 이번 조사용으로만 추가 — 조사가 끝나면 제거할지 유지할지는 PASS 확정 후 정리)에 한 줄 기록한다. 이 로그는 사용자가 실제로 영상을 재생해본 뒤 "방금 세션에서 fps 표시용 객체가 몇 번 생성됐는지"를 파일로 확인할 수 있게 해준다 — 두 번 이상 생성됐다면 재생/정지 버튼의 `st.rerun()`이 범인이라는 뜻이고, 한 번만 생성됐는데도 중복이 보인다면 완전히 다른 원인(프론트엔드/브라우저 쪽)을 찾아야 한다는 뜻이다.
3. 어느 쪽이든, 수정 후 **반드시 실제로 `streamlit run app.py`를 띄우고 로컬 영상을 재생해 FPS가 한 줄로만 보이는지 확인**하라. 지난 두 번 모두 "코드는 고쳤지만 실제 브라우저에서 확인 못 함"으로 끝났다가 사용자가 재현한 전적이 있다 — 이번엔 가능한 모든 수단(헤드리스 브라우저가 샌드박스 제약으로 막히면, 최소한 1번의 fragment 갱신이 실제로 일어나는지 서버 로그나 `st.session_state` 값 변화로 간접 확인 등)을 동원해 최대한 실증적으로 확인하고, 안 되면 "왜 안 됐는지"를 테스트 결과에 구체적으로 남겨라.

### FPS 중복 원인 확정 — 화면 식별자로 "진짜 서로 다른 두 요소"임을 증명함 (2026-10-13, Claude)

사용자가 재생 버튼을 누른 뒤 화면에 보인 두 줄의 `[xxxx]` 식별자가 **서로 달랐다**고 확인했다. 즉 지금까지의 모든 가설 중 "같은 `fps_ph` 객체가 어떤 이유로 두 번 그려지는 것"은 아니고, **실제로 서로 다른 두 번의 스크립트 실행에서 각자 만든 `st.empty()` placeholder가 둘 다 화면에 남아있다.** 하나(오래된 식별자)는 "▶ 시작"을 누르기 전 idle 상태의 실행이 만든 것이고, 다른 하나(새 식별자)는 재생을 시작한 이후 while 루프에서 계속 갱신 중인 것으로 보인다 — idle 실행의 `fps_ph`가 재생이 시작된 뒤에도 화면에서 제대로 치워지지 않고 남아있는 것이다.

**수정 방향(추측이 아니라 구조적으로 확실한 방법)**: `fps_ph = st.empty()`가 `with settings_col:` 블록 안, 여러 조건부 위젯(소스 선택 라디오, 파일 업로더/RTSP 선택, 야간 밝기 보정 라디오 등)보다 한참 뒤에 깊이 중첩된 위치에서 만들어지고 있다. 이렇게 조건문이 많이 끼어있는 위치에 `st.empty()`를 두면, idle 상태와 재생 중 상태 사이에 그 앞의 렌더링 트리가 미세하게 달라질 때 Streamlit이 같은 자리로 인식하지 못하고 "새 요소"로 취급해 이전 요소가 고아로 남을 수 있다.

**지시**: `fps_ph`(및 FPS 표시 관련 코드)를 **스크립트에서 가장 바깥쪽, 조건문에 거의 영향받지 않는 안정적인 위치**로 옮겨라 — 예를 들어 `settings_col`/`canvas_col` 같은 컬럼 분기보다 훨씬 앞쪽, 세션 상태 초기화 직후처럼 **매 실행마다 100% 동일한 코드 경로로 도달하는 지점**에 `fps_ph = st.empty()`를 두고, 실제 화면상 위치(영상 소스 설정 패널 맨 아래)는 Streamlit의 레이아웃 기능(예: 미리 자리만 잡아두고 나중에 그 컨테이너에 내용을 채우는 방식, 또는 `st.container()`를 활용해 시각적 위치와 생성 시점을 분리하는 방법)으로 맞춰라. 정확히 어떤 Streamlit API 조합이 가장 깔끔할지는 Codex가 실제 구조를 보고 판단하되, **핵심 원칙은 "fps_ph가 생성되는 코드 경로가 idle 상태와 재생 중 상태에서 완전히 동일해야 한다"**는 것이다.

이 수정 후에도 화면 식별자는 그대로 남겨두고(이미 결정적 증거를 얻는 데 유용했으니), 사용자가 다시 한번 재생해서 **이번엔 한 줄만 보이는지, 식별자가 하나만 뜨는지** 확인해야 한다고 테스트 결과에 명시하라. 만약 여전히 두 줄이 보이면 이번엔 어느 식별자가 새로 생긴 것인지(idle 쪽인지 재생 중 쪽인지) 등 더 구체적인 정보를 요청할 수 있게 준비하라.

### 최종 종결 — 사용자 최종 확인 (2026-10-13, Claude)

사용자가 디버그 식별자 제거와 구분선 중복 해결까지 실제 화면에서 확인했다. 이 작업은 총 8라운드를 거쳤다: 1차 fps_ph None 크래시 + ROI 메시지 위치 이동 → (타임아웃) → 2차 None 크래시 수정 → 3차 ROI 오류 메시지 위치 복원 → (최재원님 multi-ROI PR #23과 브랜치 충돌, Claude가 직접 병합) → 4차 FPS 중복 화면 식별자로 원인 확정(서로 다른 두 요소가 동시 존재) → 5차 `fps_panel`을 안정적인 별도 컨테이너로 분리해 근본 해결 → 6차 디버그 코드 정리 + 같은 원인으로 발생한 구분선 중복 수정.
